# Branta Rust SDK

If you are implementing this SDK in a consumer project, see the **Integration Guide** section at the top of `README.md` — it covers integration types, recommended flows, and rules.

---

## Developer notes (SDK contributors)

### Crate layout
- `src/enums.rs`, `src/options.rs`, `src/error.rs`, `src/extensions.rs`, `src/models.rs` — shared primitives (base URL enum, privacy mode, destination type, `BrantaClientOptions`, `BrantaError`, hash-ZK helpers, wire models).
- `src/v2/` — the only supported API surface:
  - `service.rs` — orchestrates ZK encrypt/decrypt around HTTP calls (`BrantaService`, the public entry point).
  - `client.rs` — raw HTTP client (`BrantaClient`); do not call directly from consumer code.
  - `builder.rs` — `PaymentBuilder`.
  - `parser.rs` — `QrParser`/`QrDestination`.
  - `encryption.rs` — AES-256-GCM encrypt/decrypt (`AesEncryptionTrait`/`AesEncryptionService`).
  - `secret_generator.rs` — `SecretGeneratorTrait`/`GuidSecretGenerator`.
- `examples/branta_example.rs` — runnable end-to-end demo; README code samples are copied from this, not hand-written independently.
- `tests/integration_test.rs` — live staging/production lookups, gated by `BRANTA_SKIP_INTEGRATION`.

### Build / test / release
- Build: `cargo build`
- Test: `cargo test` (unit tests + the mocked `BrantaService` suite + integration tests — the latter hit real network by default)
- Skip integration tests: `BRANTA_SKIP_INTEGRATION=1 cargo test`
- Lint: `cargo clippy --all-targets -- -D warnings`
- Format: `cargo fmt --check`
- Release: bump `version` in `Cargo.toml`, add a `CHANGELOG.md` entry, `cargo publish`

### Key behaviors to preserve
- **`PrivacyMode::Strict` is the default.** It forbids plain-text on-chain lookups (`get_payments` returns `Err(BrantaError::PrivacyModeViolation)`; `get_payments_by_qr_code` returns an empty `PaymentsResult` with a populated `verify_url`) and forbids non-ZK destinations on `add_payment`. `Loose` removes those restrictions. Note the nuance in `get_payments`: supplying *any* `destination_encryption_key` bypasses the Strict plain-lookup ban, even for a non-hash-ZK value — only `hash_zk_type.is_none() && destination_encryption_key.is_none() && Strict` errors.
- **`verify_url` is always returned**, including on a miss.
- **ZK destinations.** Bitcoin addresses are encrypted with one shared random secret per `add_payment` call (UUID v4 via `GuidSecretGenerator`); hash-ZK types use a deterministic key derived from `SHA-256(lowercase(value))`. **Only `Bolt11`, `ArkAddress`, and `SilentPayment` are hash-ZK types** — `Bolt12`/`LnUrl`/`LnAddress`/`TetherAddress` are valid `DestinationType`s but `get_hash_zk_type` must keep returning `None` for them. Don't "fix" this.
- **Decryption failures are silently swallowed** inside `BrantaService` — a destination that fails to decrypt (wrong key, mismatched type) is simply left with `is_encrypted = true`, never surfaced as an `Err`. Metadata/DEK decryption follows the same rule, and is only attempted once per payment (guarded by `payment.is_metadata_decrypted`).
- **GET lookups never error.** Non-2xx, empty body, malformed JSON, or a transport failure all degrade to `Ok(vec![])` inside `BrantaClient::get_payments` — never propagate. Only `add_payment`'s POST and the logo-domain check are allowed to return a real error.
- **Crypto wire format must byte-for-byte match every sibling SDK** — see the doc comments on `src/v2/encryption.rs` before changing anything there. There's a checked-in cross-SDK fixed vector test (`cross_sdk_fixed_vector_matches_python`) generated by actually running `branta-python`; if you ever need a new one, run the equivalent Python/Kotlin call rather than hand-deriving expected bytes.
- **No retry logic, no configurable timeout.** This was explicitly removed from `branta-dotnet`'s history — don't reintroduce either.

### Known cross-SDK inconsistencies (do not "fix" unilaterally — coordinate across all six repos first)
- `branta-kotlin` serializes the BTCPay field as `btcpay_server_plugin_version`; every other SDK (including this one) uses `btc_pay_server_plugin_version`.

### Logo-URL domain validation
`BrantaClient::verify_logo_urls` checks every payment in a GET response (never just the first), and every logo-bearing field: `platform_logo_url`, `platform_logo_light_url`, `parent_platform.logo_url`/`logo_light_url`, and `child_platform.logo_url`/`logo_light_url`. A mismatch returns `BrantaError::LogoUrlDomainMismatch(field)`, naming the offending field. Historical note: dotnet/js/dart/python previously had an early-`return`-instead-of-`continue` bug here that only checked the first payment, and all six SDKs previously checked only `platform_logo_url`; both gaps were closed across the sextet in the 2026-09 logo-URL validation hardening. This Rust port never had the `return`/`continue` bug (it always used `continue`).

### Conventions
- Public API is flat at the crate root (`branta::BrantaService`, etc.) and also available under `branta::v2::*`.
- `BrantaClientOptions` can be passed per-call as `Option<&BrantaClientOptions>` to override constructor defaults, field-by-field (`get_base_url`/`get_privacy`/`get_api_key`/`get_hmac_secret` in `options.rs`).
- `BrantaService::new(options)` for production use (real `BrantaClient`/`AesEncryptionService`/`GuidSecretGenerator`); `BrantaService::with_deps(options, client, aes, secret_generator)` injecting `Box<dyn Trait>` for tests. Mocks are generated via `mockall::automock` on `BrantaClientTrait`/`AesEncryptionTrait`/`SecretGeneratorTrait`.
- `QrParser::new` is infallible by design — no sibling SDK ever raises a QR-parse error; unrecognized input just yields an untyped destination.
- Keep parity with `branta-dotnet`, `branta-js`, `branta-dart`, `branta-python`, `branta-kotlin`: any new method, option, or enum value here must be reflected in all five, and vice versa.
